# CodeCleaners.PgProj

PostgreSQL project tooling: a hand-written SQL parser + semantic model, a deploy/sync engine, and
a local CLI (`PgProj.Cli`, a local test tool). Validated **locally** with `dotnet test` — there is
no GitHub CI by design (see the hard rule below).

## CI/CD on GitHub — USER DECISION ONLY (hard rule)

**Touching any *online* GitHub infrastructure for CI/CD is the user's decision, never the
assistant's.** Do NOT, on your own initiative, create, edit, enable, disable, trigger, re-run, or
delete any of:

- GitHub Actions workflows (`.github/workflows/*`) or composite actions (`.github/actions/*`)
- workflow runs, hosted/self-hosted runners, environments, Actions secrets, or Actions settings
- branch protection, required-status-checks, or merge-queue configuration
- anything via the `gh` CLI or the GitHub API that changes CI/CD state online

Act on these **only** when the user explicitly instructs it in that request. The project is
intentionally validated locally (`dotnet test`), not via paid GitHub Actions minutes. If a task
appears to need CI/CD, surface it and ask — do not implement it. (The Azure DevOps template under
`ci/azure-devops/` is an opt-in artifact and likewise must not be wired to run without the user
saying so.)

## Build & test (local)

```bash
dotnet build PgProj.slnx -c Release
dotnet test  tests/PgProj.Core.Tests -c Release   # full suite; keep 100% green (round-trip parity)
```

Parser/engine performance work is benchmark-gated: `bench/PgProj.Benchmarks` (BenchmarkDotNet,
`[MemoryDiagnoser]`); `dotnet run --project bench/PgProj.Benchmarks -c Release -- alloc` is a fast
bytes/op probe. No perf change ships without a measured allocation delta.

## Performance dashboard — publish gains on commit

The progress dashboard lives at **`docs/parser-performance.md`** (GitHub-rendered, with the
`docs/parser-perf-*.svg` charts) and is linked from the README.

**When a commit produces a measured allocation gain, update the dashboard in that same commit:**

1. Confirm the gain with numbers — the `bench -- alloc` probe and/or a BDN A/B
   (`PipelineBenchmarks`); allocation (bytes/op) is the metric, not noisy ShortRun wall-clock.
2. Append the new stage to the §1 "All"-bucket journey (tag + MB/op) and refresh the §2 per-bucket
   chart + both tables and the cumulative % / headline. Regenerate the SVGs the same way they were
   produced (PowerShell emitting `docs/parser-perf-journey.svg` / `parser-perf-buckets.svg`).
3. Keep the [[parser-perf-optimizations]] memory's win log in sync.

No measured gain, or a delta within benchmark noise → **do not touch** the dashboard. This is a
**manual step performed as part of the commit** — do NOT add a git hook, GitHub Action, or any CI
job to run benchmarks or publish stats automatically (benchmarks take minutes, and the CI/CD hard
rule above stands). "Publish" here means committing the updated Markdown + SVGs to the repo, which
renders on GitHub; it does not mean any online CI/CD.

## Lab Notes

- 2026-06-12 — **VS 2026's `devenv /updateconfiguration` rebuilds the MEF ComponentModelCache WITHOUT scanning per-user extensions** (`%LOCALAPPDATA%\...\18.0_*\Extensions`), and the next IDE start trusts that cache — so a per-user VSIX's MEF parts (content types, classifiers, ILanguageClient) silently never compose: pkgdef things (commands, editor factory, project type) work while ALL editor MEF features are dead, with NO entry in `ComponentModelCache\*.err` (the assembly is never scanned; VS 2022's same-day cache had it). Diagnose by string-scanning `ComponentModelCache\Microsoft.VisualStudio.Default.catalogs` for the dll name. Fix: delete the instance's `ComponentModelCache` dir and start VS (in-IDE rebuild DOES scan per-user) — `install-pgproj.cmd` step 4 now purges it on every install. How to apply: any "MEF export from the classic VSIX doesn't activate in the installed product" — check the catalogs file FIRST, before suspecting the export/manifest.
- 2026-06-12 — The reference/semantic gate (`ReferenceResolver` + `ReferenceValidator.Validate` — unresolved relations, bad columns, type errors) is NOT part of `ProjectBuildResult.UnifiedDiagnostics`; `pgproj build` runs it as a separate CLI step after BuildAsync. Any consumer claiming "same verdict as build" (the LSP did) must call the gate too, and must read files via `DatabaseProject.ReadEffectiveText` (overlay/substitution-aware) — raw `SourceReader.ReadAllText` bypasses the LSP's unsaved-buffer overlay. `LanguageService.ComputeEngineDiagnosticsForFileAsync` now does both. How to apply: new build-parity surface (editor, CI annotator) = UnifiedDiagnostics + reference gate, never UnifiedDiagnostics alone.
- 2026-06-12 — **The .pgproj PostgreSQL editor was dead in the installed product for TWO stacked reasons, both silent** (every layer in between was healthy: registration priority 1000 ✓, package load ✓, factory CLAIM ✓, MEF catalog ✓): (1) after `CreateEditorInstance` returns, the text docdata's file-load runs language detection by extension and OVERWRITES the explicitly-set content type — the buffer must also set `VsBufferDetectLangSID=false` (IVsUserData) or "pgsql" silently reverts to plain text (no classifier, no anything); (2) the LSP broker only activates an `ILanguageClient` whose content type derives from `CodeRemoteContentDefinition.CodeRemoteContentTypeName` — with `BaseDefinition("code")` the client composes into MEF but is NEVER started (no gold bar, no log). Found via the VM harness loop: factory ActivityLog instrumentation (run devenv with `/log` LAST on the cmdline) + per-link environment diagnostics in the failure report. How to apply: any per-buffer content-type assignment needs both UserData keys; any new LSP-bound content type needs the CodeRemote base (+ "code" for editor features); when an editor chain "does nothing", walk the links IN ORDER — registration → package load → claim (instrument it) → MEF catalog → content type survival → broker base-type gate.
- 2026-06-12 — CPS hierarchy facts learned diagnosing the above: a file opened BEFORE the project materializes gets a virtual-folder hierarchy (`VSHPROPID_TypeGuid` = {6bb5f8f0-…}, capabilities E_NOTIMPL) and PERMANENTLY lands in the fallback editor; once loaded, the real CPS hierarchy answers TypeGuid with the project type guid AND `VSHPROPID_ProjectCapabilities` (the factory now accepts either). DTE `Project.Kind` says the type guid even while the doc association is missing — don't trust it alone. DTE-over-ROT on VS 2026: `Marshal.GetActiveObject("VisualStudio.DTE.18.0")` finds nothing — enumerate the ROT for the pid-suffixed moniker (`!VisualStudio.DTE.18.0:<pid>`). DTE `ToolWindows` doesn't dispatch on the ROT object (DTE v1 default interface) — go `Windows.Item(vsWindowKindErrorList).Object`; LSP diagnostics do NOT surface in legacy `ErrorItems` (modern error table) — read the Error List via UIA.
- 2026-06-12 — UIA-scan checks need their TOOL WINDOW to exist: a fresh VS instance has the Error List CLOSED, and a FindFirstDescendant(ByName('Error List')) scan just returns false forever - the LSP wire log (new: set PGPROJ_LSP_LOG=<file> before `pgproj serve` / devenv) proved the server publishing diagnostics that 'never appeared'. How to apply: any UIA assertion on a tool window must OPEN it first (View.ErrorList et al.); when diagnostics 'never arrive', check the wire log BEFORE touching server code.

- 2026-06-25 — Standalone `ALTER TABLE … ADD CONSTRAINT` (FK/PK/UNIQUE/CHECK) is the form `pgproj extract` emits, and it was NOT folded into the core model (`ModelBuilder` had no `AlterStatement` case; the parser kept only the action verb "ADD CONSTRAINT", discarding the parsed constraint), so the comparer/deploy/test-gen never saw those FKs — only `TableDesigner.CollectCompanions` folded them, for its own round-trip. Fix: capture `ParseTableConstraint`'s result into `AlterStatement.AddedConstraints` and apply it in `ModelBuilder` (reusing `AddTable`'s constraint switch via a shared `ApplyTableConstraint`); same-file CREATE-before-ALTER means the table is present when the ALTER is processed. GOTCHA: this then DOUBLE-folded with `TableDesigner` (every FK appeared twice → 183 test failures, all `Assert.Single → 2 items`), because the designer's `table` already came through `ModelBuilder`. Reconcile by deleting the designer's manual fold and skipping any `ALTER` whose `AddedConstraints.Count > 0` (re-emitted from the model now). How to apply: folding a previously-ignored statement into the core model means hunting every OTHER consumer that compensated for the gap (designer companions here) — grep for the node type before assuming the fold is additive; a `Single → 2` failure storm is the signature of a double-fold.
- 2026-06-25 — When a generated INSERT supplies an explicit value to a `GENERATED ALWAYS AS IDENTITY` column, the statement needs `OVERRIDING SYSTEM VALUE` or PG rejects it with `428C9` — and the override must fire for EVERY value source that fills such a column (a forced PK/unique key, an FK value, AND a seeded depth-1 parent's referenced-key override), not just the obvious "forced key" branch; `NULL` is exempt (it's the absence of a value, e.g. a NOT-NULL negative test). Bug caught in `BaselineRowSynthesizer` (#154) before any live run because the seeded-parent insert came through the `overrides` path, which originally skipped the identity-always check. How to apply: any code synthesizing INSERTs from the model must set `OVERRIDING SYSTEM VALUE` based on the COLUMN being identity-always, decided at emit time regardless of where the value came from — never gate it on one code path.
- 2026-07-01 — `pgproj test generate` was reshaped (owner decision) from emitting `.test.sql` (run by the bespoke `PgUnitRunner`) to emitting a **standalone xUnit C# project** (`XunitSuiteScaffolder`): Testcontainers spins its own PG, greenfield schema deploys once, each test runs in a rolled-back transaction — so `dotnet test`/VS Test Explorer is the only runner (CI-friendly, no PgProj tooling). The whole SQL path (`SuiteScaffolder`/`TestScaffolder`/`PgUnitRunner`/`pgproj test <proj>`/`test scaffold`) was DELETED; `BaselineRowSynthesizer` is KEPT and reused (its INSERT/prelude SQL is embedded in C# tests). - 2026-06-11 — A `.pgproj` would not LOAD in the VS IDE (only `dotnet build` worked) — error *"the project is missing some critical imports or the referenced SDK cannot be found."* Root cause (found by running VS's own MSBuild `/pp` on a fresh project): `PgProj.Sdk` did not import `Microsoft.Common.props`/`.targets`. Fix: **compose `PgProj.Sdk` on `Microsoft.Build.NoTargets`** (3.7.134) — `Sdk/Sdk.props` imports `<Import Sdk="Microsoft.Build.NoTargets" Project="Sdk.props"/>` (after setting `TargetFramework=netstandard2.0` + `EnableDefaultItems=false`, which Common.props reads), `Sdk/Sdk.targets` imports NoTargets' `Sdk.targets`, and the `pgproj build` is hooked via `<Target _PgProjBuild AfterTargets="Build">` (NoTargets compiles nothing; AfterTargets="Build" keeps it off the IDE's design-time builds). `Publish` is defined after the import so it overrides Common's. Removed our old hand-rolled `Build`/`Clean`/`Rebuild`/`Restore` targets (Common provides them). Verified: `/pp` now shows Common.props+targets+CompileDesignTime present (expanded 13KB→1.48MB), and `dotnet build` still emits model+pgpkg via the CLI for BOTH the `Sdk="PgProj.Sdk/0.1.0"` and explicit-`<Import>` sample forms. This is the same pattern MSBuild.Sdk.SqlProj uses to be VS-loadable. NoTargets resolves from nuget.org (needs network on first project open). DIAGNOSTIC TRAP that wasted time: `devenv /log <path>` treats `<path>` as the LOG FILE and overwrites it — never pass a project to `/log`; to evaluate a project the way VS does, run the VS `MSBuild.exe` (amd64) with `/t:Restore` then `/pp:out.xml` and inspect, no devenv needed.

- 2026-06-11 — VisualStudio.Extensibility `CommandConfiguration` is COMPILE-TIME evaluated: any user-defined helper method/property in the initializer fails the build with CEE0018 ("invocation of user-defined methods is not supported"). Why: the OOP model serializes the configuration into `.vsextension/extension.json` at build time. How to apply: inline everything — `CommandPlacement.VsctParent(new Guid("literal"), 0x1020, priority: 0x0100)`, literal regex strings in `ActivationConstraint.ClientContext` — and verify by reading `.vsextension/extension.json` inside the built vsix (controlPlacements/commandSets sections). VsctParent can target a VSCT group owned by ANOTHER installed extension (our classic one) — that's how OOP commands land on the .pgproj project context menu without any Extensions-menu entry.
- 2026-06-11 — A `.cmd`/`.bat` MUST be saved CRLF + ASCII (no BOM); the Write tool emits LF, which cmd.exe silently mis-parses — `setlocal`/`set` stop expanding, `%VAR%` prints literally, and command lines get chopped (`'m' is not recognized`, empty Configuration), so the batch "runs" but does the wrong thing with exit 1. Why: cmd is line-ending- and codepage-sensitive in a way PowerShell/SQL aren't; em-dashes in `rem` comments also break it. How to apply: after Writing any batch file, normalize it — `$c=[IO.File]::ReadAllText($p); $c=$c.Replace([char]0x2014,'-'); $c=($c -replace "`r`n","`n") -replace "`n","`r`n"; [IO.File]::WriteAllText($p,$c,(New-Object Text.ASCIIEncoding))` — then run it once to confirm. (`editors/vs/build-vsix.cmd` builds all three VS artifacts in order; it was the casualty that taught this.)
- 2026-06-11 — You CANNOT embed/bundle a VisualStudio.Extensibility (OOP) extension inside a VSIX extension pack: VSIXInstaller's nested-install path throws `System.InvalidOperationException: Cannot install a VisualStudio.Extensibility extension using the install call. Must unzip and call the finalizer instead.` (stack: `ExtensionInstallModule.InstallNestedExtensions` → `InstallInternal`). Why: the legacy nested installer predates the OOP install flow. So the `d:InstallSource="Embed"` pack (bundling both child vsixes in one .vsix for offline one-click) is a DEAD END whenever a child is an OOP extension — it builds fine but fails AT INSTALL. How to apply two ways: (a) LOCAL/offline → don't pack; run `VSIXInstaller.exe` on each child vsix directly (that path supports OOP). `editors/vs/install-pgproj.cmd` does this (uninstall old Ids `/quiet` then install both; uninstall-first matters because same-version dev rebuilds otherwise hit "already installed" and don't replace). (b) MARKETPLACE → use a REFERENCE pack: `editors/vs/PgProj.VisualStudio.ExtensionPack` is content-only (net472, `IncludeAssemblyInVSIXContainer=false`), manifest `<Dependency d:Source="Installed" Id="<child Identity>" Version="[x,)" />` with NO Embed/Location/bundled Content — VS resolves each Id from the Marketplace and installs it individually (correct per-extension flow). Reference-pack Ids/versions MUST match the published children (OOP `…-000000000025` v1.0.0.0, classic `…b0000000-0025` v0.1.0); `Dependency DisplayName` has a ~50-char MaxLength (VSSDK1062). The pack is Marketplace-ONLY: double-clicking the reference vsix locally fails (deps resolve against the Marketplace). NuGet (`PgProj.Sdk`) is the third, complementary channel — it can't carry a project type or extension, only the MSBuild SDK + CLI for headless build/publish.

- 2026-06-11 — **ROOT CAUSE of the unloadable classic package**: the generated pkgdef registered the package with `"Assembly"="PgProj.VisualStudio.ProjectSystem, Version=..."` (name-based CLR binding via GAC/probing paths, which do NOT include the extension folder), so `CreateInstance` died with FileNotFoundException — "The 'PgProjPackage' package did not load correctly" (only visible once the autoload above forced a load attempt; before that the package just silently never loaded). How to apply: every VSIX-deployed classic package in this repo needs RegisterWithCodebase=true; verify by reading the built pkgdef (UTF-16) and looking for "CodeBase"= not "Assembly"=.
